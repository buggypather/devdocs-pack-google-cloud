GKE known issues

This page lists known issues for GKE. This page is for Admins and architects who manage the lifecycle of the underlying technology infrastructure, and respond to alerts and pages when service level objectives (SLOs) aren't met or applications fail.

This page lists known issues for all supported versions and for the two minor versions that immediately precede the earliest version in extended support. After a version reaches the end of extended support, all N-2 issues are removed. For example, when version 1.30 reaches the end of extended support, known issues specific to versions 1.28 and earlier are removed.

Pods remain in the Pending state when a built-in Autopilot ComputeClass is the cluster-level default

If you set a built-in Autopilot ComputeClass (such as autopilot or autopilot-spot) as the cluster-level default by using the --default-compute-class flag, GKE creates a default ComputeClass with the whenUnsatisfiable: field set to DoNotScaleUp. Pods that don't select a ComputeClass and that need nodes that the general-purpose Autopilot platform can't create might remain in the Pending state when a new node is needed. For example, this issue affects Pods that request GPUs or TPUs, that select a specific machine family with the cloud.google.com/machine-family node selector, or that require Spot VMs when the default class uses on-demand VMs. Pods that fit on existing nodes aren't affected.

When the control plane upgrades to 1.37.1-gke.2432000 or later, GKE updates the default ComputeClass by setting the whenUnsatisfiable field to ScaleUpAnyway, and the issue resolves without further action.

Workaround:

Use one of the following options:

  • Select a ComputeClass explicitly in the affected workloads, or set a namespace-level default ComputeClass for their namespaces.
  • Upgrade the cluster control plane to 1.37.1-gke.2432000 or later.

HTTP POST requests for tokens from the metadata server fail with a 400 Bad Request error

Workloads that use Workload Identity Federation for GKE to authenticate to Google Cloud APIs by requesting service account access tokens or identity tokens from the GKE metadata server (such as /computeMetadata/v1/instance/service-accounts/default/token or /computeMetadata/v1/instance/service-accounts/default/identity) might fail with an HTTP 400 Bad Request (INVALID_ARGUMENT) error.

This issue occurs when an application, client library, or API gateway sends an HTTP POST request without a valid certificate chain in the request body. In affected GKE versions, POST requests to these token endpoints are strictly reserved for bound access and ID tokens. As a result, requests that have empty, form-encoded, or invalid JSON in the payloads are rejected.

To fix the issue, upgrade to the latest patch version within the minor version of any release channel.

Workaround:

To resolve this issue, configure your application, client library, or API gateway to use the GET method instead of POST when you request access or ID tokens from the metadata server, like in the following example: 

curl -H "Metadata-Flavor: Google" "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"

If your workload uses a third-party SDK or gateway (such as MuleSoft Flex Gateway, IBM App Connect, or custom HTTP scripts) that defaults to sending POST requests to metadata server endpoints, update the configuration or client library to send GET requests.

Unscheduled Pods and exhausted quota during two-step minor upgrades for the control plane.

During two-step minor version upgrades for control planes in Autopilot clusters that use extended duration Pods, new node pools might be provisioned using the earlier node version. Cluster Autoscaler evaluates the newly provisioned nodes against the upgraded control plane version, detects a version mismatch, and applies the cloud.google.com/not-target-gke-version:true taint. Cluster Autoscaler also blocks scaling up existing or newly created extended duration Pod node pools that use the earlier node version.

This behavior prevents Pods from scheduling and triggers an infinite scaling loop. Instead of scaling up an existing node pool, node auto-provisioning creates a new single-node pool on every scale-up iteration to accommodate the pending workloads. This loop generates hundreds of separate empty node pools that can eventually exhaust regional Managed instance group quotas.


Workaround:

To resolve the scaling loop, manually complete the control plane upgrade by running the following command: 

gcloud container clusters complete-control-plane-upgrade [CLUSTER_NAME] --location=[LOCATION]

Alternatively, apply the following toleration to the affected workloads so they can be scheduled on the earlier-version nodes: 

tolerations:
- key: "cloud.google.com/not-target-gke-version"
  operator: "Equal"
  value: "true"
  effect: "NoSchedule"

Nodes that mount NFS volumes accumulate mount entries and stop creating containers

On nodes running affected versions, mounting an NFS volume leaves extra entries in the node's mount table. Additionally, when a Pod using an NFS volume terminates, unmount attempts fail, causing the kubelet to repeatedly retry the unmount. Each retry adds more entries to the mount table, which causes the mount table to grow continuously even when no new workloads are scheduled.

When the mount table reaches the kernel limit, the container runtime can no longer create containers on that node. The node stops running new Pods, might report a NotReady status, and might restart repeatedly. Pods that use NFS volumes might remain in the Terminating state because their volumes can't be unmounted.

In Pod events and kubelet logs, nodes in this state report errors similar to the following:

MountVolume.SetUp failed for volume "VOLUME_NAME" : mount failed: exit status 1
mount: /etc: mount(2) system call failed: No space left on device

This issue affects node pools that mount NFS volumes with the Kubernetes in-tree NFS driver. Nodes that don't use the in-tree NFS driver to mount NFS volumes aren't affected.

Workaround:

To recover an affected node, restart or re-create it. The extra mount entries exist only in the running state of the node, so they're cleared when the node restarts. Pods that are stuck in the Terminating state after the restart can be removed with the following command:

kubectl delete pod POD_NAME --namespace NAMESPACE --force --grace-period=0

To stop the issue from recurring in Standard clusters, downgrade the node pools that mount NFS volumes to a 1.36 version. Set a maintenance exclusion so that GKE doesn't automatically upgrade the node pools back to an affected version.

If an Autopilot cluster runs an affected version, use one of the following options instead:

  • If your NFS volumes are backed by Filestore, mount them with the Filestore CSI driver instead of the in-tree NFS driver. The CSI driver mounts volumes from its own container and doesn't use the affected node component.
  • If you must keep using the in-tree NFS driver, let node auto-repair recover affected nodes. Autopilot clusters repair nodes automatically, and a node that reports a NotReady status for about 10 minutes is drained and re-created, which clears its mount table.

A4X Max (GB300) GPU workload failures

Creating or upgrading GKE A4X Max node pools (a4x-maxgpu-4g-metal) on or to specific patch versions (see the Identified version(s) column) causes GPU workload failures with the attached NVIDIA GB300 Grace Blackwell Ultra Superchips. Due to extended High Bandwidth Memory (HBM) boot times on GB300 hardware with this bare metal machine type, the nvidia-persistenced startup service times out. This timeout leaves the GPUs uninitialized, and results in the cudaErrorDeviceUnavailable(46) error message when Pods attempt to claim CUDA resources.

Solution:

Upgrade each impacted cluster and node pool to a fixed version. GKE prevents creating A4X Max node pools with affected versions, and won't automatically upgrade the node pools to affected versions. GKE doesn't prevent manual upgrades to the affected versions. However, to avoid the failures, we recommend not upgrading to the affected versions.

Workaround:

If you cannot upgrade, delete all A4X Max node pools that are running affected versions, and re-create the node pools using an earlier, unaffected version. Note that because A4X Max capacity must be obtained through a reservation, you won't forfeit any capacity by deleting the node pools.

GPU or TPU nodes stuck with impending-node-termination taints after host maintenance

On GKE clusters with accelerator nodes (GPU or TPU) that run affected versions, nodes might become stuck with the cloud.google.com/impending-node-termination or cloud.google.com/maintenance-window-started taints after Compute Engine host maintenance or repairs are completed. When the VM instance is started again, the GKE maintenance controller might prematurely re-apply these taints if there is another future maintenance event scheduled for the node, preventing new workloads from scheduling on healthy nodes.

Workaround:

To resolve the stuck state, you must manually remove both the GKE managed active maintenance labels and the taints from the affected nodes. If you only remove the taints, the GKE maintenance controller will automatically re-apply them.

To clear the labels and taints, run the following commands:

kubectl label nodes NODE_NAME cloud.google.com/active-node-maintenance-
kubectl label nodes NODE_NAME cloud.google.com/scheduled-maintenance-time-
kubectl label nodes NODE_NAME cloud.google.com/scheduled-maintenance-time-latest-
kubectl taint nodes NODE_NAME cloud.google.com/impending-node-termination-
kubectl taint nodes NODE_NAME cloud.google.com/maintenance-window-started-

Replace NODE_NAME with the name of the affected node.

Pod admission failures for TPU v7 workloads due to reporting an incorrect chip count.

GKE incorrectly advertises eight allocatable TPU chips for TPU v7 (tpu7x) accelerators with a 2x2x1 topology, which physically contains only four chips. This reporting mismatch prevents Pod scheduling for TPU v7 workloads.

The dual-chiplet architecture of TPU v7 is not correctly handled in earlier versions, resulting in Pod admission failures. Depending on the requested TPU resources, the following errors occur:

  • When requesting four TPUs (google.com/tpu: 4), the `kubelet` returns an UnexpectedAdmissionError: "invalid TPU chip count request, you must request all 4 chips on this node together".
  • When requesting eight TPUs (google.com/tpu: 8), the tpu-accelerator-topology-constraints admission webhook denies the request with the following error: "Invalid resource requests for google.com/tpu. It should be equal to one of [4] for accelerator tpu7x and topology 2x2x1".

Workaround:

To resolve this issue, upgrade the GKE cluster to version 1.34.1-gke.1829001 or later.

Lustre client does not utilize secondary NICs on multi-NIC nodes

On GKE nodes with multiple Network Interface Cards (NICs), the Managed Lustre CSI driver is enabled by default to use all available NICs to aggregate bandwidth by spreading TCP storage traffic across network interfaces. However, because of a known issue, Lustre clients starting from version 2.14.0_p249 might not utilize secondary NICs. Instead, all TCP storage traffic to the Managed Lustre instance is routed exclusively through the primary NIC, preventing bandwidth aggregation and limiting storage throughput.

Workaround:

If your workloads require multi-NIC bandwidth aggregation for Managed Lustre, downgrade your node pools to a GKE version earlier than 1.35.3-gke.1234000, such as 1.35.2-gke.1842000.

gVisor shim fails to clean up, logs "runsc: executable file not found in $PATH" error

Upon every gVisor Pod exit or OOM kill, containerd attempts to tear down the sandbox. However, the cleanup process sometimes fails, logging the error exec: "runsc": executable file not found in $PATH. This error can cause issues such as resource exhaustion, network degradation, NodeLocalDNS panic, DNS timeouts, or high latency when creating Pods.

Solution:

Upgrade the GKE nodes to version 1.35.1 or later. For Standard clusters, upgrade the node pool with the affected nodes. For Autopilot clusters, manually upgrade the Autopilot cluster to 1.35.1 or later, and GKE automatically upgrades your nodes to match the control plane version as soon as possible.

Workaround:

If you can't upgrade your cluster, do one of the following:

  • Review and increase the memory requests and limits for the gVisor pods.
  • Deploy the following privileged DaemonSet to copy the runsc binary from /home/containerd/usr/local/sbin to /home/kubernetes/bin:
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: runsc-path
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: runsc-path
  updateStrategy:
    type: RollingUpdate
  template:
    metadata:
      labels:
        app: runsc-path
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: sandbox.gke.io/runtime
                operator: In
                values:
                - gvisor
      tolerations:
        - effect: NoSchedule
          key: sandbox.gke.io/runtime
          operator: Equal
          value: gvisor
      volumes:
      - name: host
        hostPath:
          path: /
      initContainers:
      - name: copy-runsc
        image: bash
        command:
        - /usr/local/bin/bash
        - -c
        - |
          set -euo pipefail
          cp /host/home/containerd/usr/local/sbin/runsc /host/home/kubernetes/bin
          chmod a+rx /host/home/kubernetes/bin/runsc
        volumeMounts:
        - name: host
          mountPath: /host
        resources:
          requests:
            memory: 5Mi
            cpu: 5m
        securityContext:
          privileged: true
      containers:
      - image: gcr.io/google-containers/pause:3.2
        name: pause

Dynamic volumes fallback to default disk type

Workloads using dynamic volumes in GKE version 1.35.0-gke.2232000 or later might fail to schedule or attach. This issue can also cause volumes to be provisioned using the fallback hd-type (such as hyperdisk-balanced) instead of the pd-type, even on nodes that don't support Hyperdisk.

Workaround:

Pod scheduling delays on new nodes with Calico network policy enabled

On GKE clusters with Calico network policy enabled, a regression in affected versions can cause significant delays in Pod scheduling on new or re-created nodes. These delays can result in nodes remaining in a NotReady state for extended periods.

The issue is caused by the Calico CNI startup script incorrectly formatting the Kubernetes API server URL for IPv4 addresses by enclosing them in square brackets ([]). This approach leads to a URL parsing error when creating new Pod sandboxes, visible in `kubelet` logs:

Failed to create pod sandbox: rpc error: code = Unknown desc = failed to setup network for sandbox ""sandbox-id"": plugin type="calico" failed (add): error creating calico client: host must be a URL or a host:port pair: "https://[IPv4-address]:443"


Workaround:

The Calico component version is determined by the cluster's control plane version. To mitigate this issue, upgrade your cluster's control plane to one of the fixed versions. After upgrading the control plane, you must re-create the nodes in your node pools to ensure they use the correct Kubernetes API server URL format. You can achieve this by performing an in-place upgrade of your node pool to the same or a newer version or by manually re-creating your node pools.

Cilium identity duplication in GKE Dataplane V2 clusters

GKE clusters running version 1.35 with GKE Dataplane V2 enabled might experience an increase in the number of ciliumidentities.cilium.io custom resources. This issue is caused by topology.kubernetes.io labels being added to Pods in Kubernetes 1.35, which produces additional Cilium identities for each zone that a Pod from a workload is scheduled to.

In both Regional and Zonal clusters, scheduling a new workload can cause temporary Cilium identity duplication. This duplication occurs because Pods get one identity at creation time based on initial labels, and another identity after topology labels are added when the Pod is scheduled to a node. In Regional clusters, the number of identities might additionally increase by a factor proportional to the number of zones the cluster spans.

Impact:

If the total number of identities exceeds 65,535, new workloads might fail to schedule.

Workaround:

To limit the total number of identities, avoid adding labels with a large number of unique values to your Pods.

For more information, see the following Cilium documentation:

  • Identity-based security
  • Security identities

Manual upgrades should be performed from versions 1.34.3-gke.1208000 and later. If you start the upgrade from a version earlier than 1.34.3-gke.1208000, you might experience temporary issues with Pod scheduling during the upgrade process.

Race condition in gke-metrics-agent DaemonSets

When you add the cloud.google.com/gke-metrics-agent-scaling-level label to a node pool to manually increase the memory allocation of the gke-metrics-agent DaemonSet, a race condition occurs in the DaemonSet during new node creation. This race condition results in intermittent restarts and might result in lost metrics.

This issue occurs because there's a delay before the label is added to a new node in the node pool. During this delay, the DaemonSet creates a Pod with the original memory allocation on that node. After the label is applied, the DaemonSet creates a Pod that has the new memory allocation. The existing Pod isn't completely deleted when the updated Pod starts. Both of these Pods try to bind to the same port number.

Workaround:

After you add the cloud.google.com/gke-metrics-agent-scaling-level label to a node pool, restart the gke-metrics-agent DaemonSet:

kubectl -n kube-system rollout restart daemonset gke-metrics-agent

Lowered open files limit with containerd 2.0

For node pools running GKE version 1.33, which uses containerd 2.0, the default soft limit for open files (ulimit -n) for containers is lowered to 1024.

This is a change in containerd itself (see containerd PR #8924) where LimitNOFILE was removed from containerd.service as a best practice, making the default system soft limit apply.

Workloads expecting a higher default soft limit (for example, those implicitly relying on the previous higher default) might experience failures, such as Too many open files errors.

Solution:

Upgrade from an earlier 1.33 patch version to 1.33.2-gke.1043000 or later.

Workaround:

Increase the open files limit for your workloads using one of the following methods:

  • Application-Level adjustment: Modify the application code or configuration to explicitly set the ulimit -n or prlimit --nofile=524288.
  • Containerd NRI Ulimit Adjuster Plugin Use the containerd/nri ulimit-adjuster plugin to adjust the ulimit.
  • Downgrade node pool (Standard only): For Standard GKE clusters, you can temporarily downgrade your node pool to version 1.32 to avoid this issue until a permanent resolution is available.
For more information about the migration to containerd 2, see Migrate nodes to containerd 2.

Google Cloud Hyperdisk size and attachment limits

Typically, a Pod that cannot be scheduled because of a node's volume attachment limits triggers the auto-provisioning of a new node. When workloads that use a Hyperdisk volume are scheduled to a node that runs a C3 or C3D VM, node auto-provisioning does not occur and the Pod is scheduled onto the already full node.

The workload is scheduled onto the node despite the lack of an available disk attachment. The workload also fails to start because of an error like the following:

 AttachVolume.Attach failed for volume "[VOLUME NAME]" : rpc error: code = InvalidArgument desc = Failed to Attach: failed when waiting for zonal op: rpc error: code = InvalidArgument desc = operation operation-[OPERATION NUMBERS] failed (UNSUPPORTED_OPERATION): Maximum hyperdisk-balanced disks count should be less than or equal to [16], Requested : [17]

The problem is present for all Hyperdisk products on C3 and C3D machines because the Compute Engine Persistent Disk CSI driver reports the 127 Persistent Disk attachment limit to the Kubernetes scheduler rather than the lower per-type Hyperdisk attachment limit.

Hyperdisk attachment limits vary by VM vCPU count and Hyperdisk product. For more information, see Hyperdisk performance limits.

Workaround:

Use one of the following workarounds:

  • Use a machine series that supports only Hyperdisk, such as C4 or C4D.
  • For standard node pools, override the node's advertised attachment limit by applying the node-restriction.kubernetes.io/gke-volume-attach-limit-override node label. For instructions, see Override persistent volume attach limits.
  • For node auto-provisioning, configure C3D nodes with at least 60 vCPUs (or C3 nodes with at least 22 vCPUs) to raise the per-VM limit for Hyperdisk Balanced and Hyperdisk ML from 16 to 32 volumes, or use Pod anti-affinity or topology spread constraints to cap the number of Hyperdisk-mounting Pods per node.

Pods using io_uring-related syscalls might be stuck in Terminating

Pods that use io_uring-related syscalls might enter the D (disk sleep) state, which is also called TASK_UNINTERRUPTIBLE, due to a bug in the Linux kernel. Processes in D state cannot be woken by signals, including SIGKILL.

When a Pod is affected by this known issue, its containers might fail to terminate normally. In the containerd logs, you might observe repeated messages similar to the following: Kill container [container-id] indicating that the system is repeatedly attempting to stop a container.
Concurrently, the kubelet logs display error messages, such as the following:

"Kill container failed" err="rpc error: code = DeadlineExceeded desc = context deadline exceeded"

or

"Error syncing pod, skipping" err="[failed to \"KillContainer\" for \"container-name\" with KillContainerError: \"rpc error: code = DeadlineExceeded desc = an error occurs during waiting for container \\\"container-id\\\" to be killed: wait container \\\"container-id\\\": context deadline exceeded\", failed to \"KillPodSandbox\" for \"pod-uuid\" with KillPodSandboxError: \"rpc error: code = DeadlineExceeded desc = context deadline exceeded\"]" pod="pod-name" podUID="pod-uuid"

These symptoms point to processes within the container that are stuck in an uninterruptible sleep (D-state), which prevents proper termination of the Pod.

Workloads that use io_uring directly, or that use io_uring indirectly through a language runtime like NodeJS, might be affected by this known issue. Affected workloads have a process in the D (disk sleep) state in the /proc/<pid>/state file, and show the io_uring string as part of the contents of /proc/<pid>/stack. NodeJS workloads might be able to disable the use of io_uring through UV_USE_IO_URING=0.

Workaround:

Upgrade the cluster nodes to a fixed version or later.

Increased Pod eviction rates on GKE versions 1.30 and 1.31

Some versions of GKE 1.30 and GKE 1.31 that use COS 113 and COS 117, respectively, have kernels that were built with the option CONFIG_LRU_GEN_ENABLED=y. This option enables the kernel feature Multi-Gen LRU, which causes the kubelet to miscalculate memory usage and might lead to the kubelet evicting Pods.

The config option CONFIG_LRU_GEN_ENABLED is disabled in cos-113-18244-151-96 and cos-117-18613-0-76.

You might not always see an unusual Pod eviction rate because this issue depends on the workload's memory usage pattern. There is a higher risk of the kubelet evicting Pods for workloads that haven't set a memory limit in the resources field. This is because the workloads might request more memory than what the kubelet reports as available.

If you see higher memory usage of an application after upgrading to the mentioned GKE versions without any other changes, then you might be affected by the kernel option.

To check if there are unusual Pod eviction rates, analyze the following metrics with Metrics Explorer: kubernetes.io/container_memory_used_bytes and kubernetes.io/container_memory_request_bytes

You can use the following PromQL queries. Replace the values for cluster_name, namespace_name, metadata_system_top_level_controller_type and metadata_system_top_level_controller_name with the workload name and type that you want to analyze:

max by (pod_name)(max_over_time(kubernetes_io:container_memory_used_bytes{monitored_resource="k8s_container",memory_type="non-evictable",cluster_name="REPLACE_cluster_name",namespace_name="REPLACE_namespace",metadata_system_top_level_controller_type="REPLACE_controller_type",metadata_system_top_level_controller_name="REPLACE_controller_name"}[${__interval}]))

sum by (pod_name)(avg_over_time(kubernetes_io:container_memory_request_bytes{monitored_resource="k8s_container",cluster_name="REPLACE_cluster_name",namespace_name="REPLACE_namespace",metadata_system_top_level_controller_type="REPLACE_controller_type",metadata_system_top_level_controller_name="REPLACE_controller_name"}[${__interval}]))

If you see unusual spikes in the memory usage that go above the requested memory, the workload might be getting evicted more often.

Workaround

If you can't upgrade to the fixed versions and if you're running in a GKE environment where you can deploy privileged Pods, you can disable the Multi-Gen LRU option by using a DaemonSet.

  1. Update the GKE node pools from where you want to run the DaemonSet with an annotation to disable the Multi-Gen LRU option. For example, disable-mglru: "true".
  2. Update the nodeSelector parameter in the DaemonSet manifest with the same annotation you used in the preceding step. For example, see the disable-mglru.yaml file in the GoogleCloudPlatform/k8s-node-tools repository.
  3. Deploy the DaemonSet to your cluster.

After the DaemonSet is running in all the selected node pools, the change is effective immediately and the kubelet memory usage calculation is back to normal.
