Govern agents with Agent Gateway

Agent Gateway lets you govern outbound traffic from AI agents that you build and host on Cloud Run. By routing egress traffic from your Cloud Run service through a self-managed Agent Gateway that runs on Secure Web Proxy, you can enforce centralized access policies, inspect payloads for content safety, and collect observability telemetry across your agentic workloads.

This document describes how to configure a centralized architecture for Agent Gateway on Cloud Run and covers how to do the following:

  • Establish required Identity and Access Management (IAM) roles and prerequisites
  • Create a self-managed Agent Gateway
  • Configure Cloud Run ambient networking to access the Traffic Director API
  • Deploy or update a Cloud Run service with ambient networking and Direct VPC egress
  • Configure your Cloud Run agent to trust Agent Gateway
  • Route egress traffic to Agent Gateway
  • Configure access and content security policies on Agent Gateway
  • Configure a centralized cross-project deployment with Shared VPC

Architecture

In a centralized self-managed deployment, Secure Web Proxy acts as the policy enforcement point and runs inside your Virtual Private Cloud (VPC) network. The ambient networking sidecar container intercepts outbound traffic from your Cloud Run agent and routes it through Direct VPC egress to your Secure Web Proxy instance. Secure Web Proxy enforces access and content rules from policy decision points such as Identity-Aware Proxy (IAP) and Model Armor.

To route and govern traffic in this architecture, you configure the following components:

  • Direct VPC egress and ambient networking: Your Cloud Run service connects to your VPC network with --vpc-egress=all and --ambient-networking, which uses the regional scope by default and routes all outbound traffic into your VPC network.
  • Self-managed Agent Gateway: A logical Agent Gateway resource in self-managed mode points to the Secure Web Proxy instance in your VPC network.
  • Egress routing policy: A Network Services API EgressRouting policy directs outbound traffic from your Cloud Run service to your Secure Web Proxy instance.
Note: You don't need Private Service Connect network attachments for Agent Gateway because the Secure Web Proxy instance runs in your VPC network. To prevent agents from bypassing the gateway, configure VPC firewall rules so that your Cloud Run subnet sends egress traffic only to your Secure Web Proxy instance.

Create a self-managed Agent Gateway

Before creating the Agent Gateway resource, deploy and configure a Secure Web Proxy instance in your VPC network as described in Deploy Secure Web Proxy as an Agent Gateway:

  1. Set up TLS inspection and create a gateway security policy that attaches your TlsInspectionPolicy. You don't need Secure Web Proxy security policy rules or URL lists.
  2. Create a ServerTlsPolicy resource with allowOpen: false and mtlsPolicy.clientValidationMode: ALLOW_INVALID_OR_MISSING_CLIENT_CERT. Don't set clientValidationTrustConfig.
  3. Deploy a Secure Web Proxy instance in explicit proxy routing mode with addresses, ports, certificateUrls, gatewaySecurityPolicy, and serverTlsPolicy configured when you create the gateway so that Cloud Run passes your agent's workload identity to Secure Web Proxy and IAP over mTLS.
Important: You must configure serverTlsPolicy, certificateUrls, addresses, and ports when you create your Secure Web Proxy instance. Updates to an existing Secure Web Proxy instance's serverTlsPolicy, certificateUrls, addresses, or ports don't propagate to the Traffic Director API. To replace these settings later, see Troubleshoot Agent Gateway.

After your Secure Web Proxy instance is ready, create a self-managed Agent Gateway resource that points to your Secure Web Proxy instance:

  1. Create a YAML configuration file named my-agent-gateway.yaml:

    name: AGENT_GATEWAY_NAME
registries:
  - "//agentregistry.googleapis.com/projects/PROJECT_ID/locations/REGION"
selfManaged:
  resourceUris:
    - "projects/PROJECT_ID/locations/REGION/gateways/SWP_NAME"

    Replace the following:

    • AGENT_GATEWAY_NAME: the name that you want to assign to your Agent Gateway resource.
    • PROJECT_ID: the project ID that hosts your Secure Web Proxy instance.
    • REGION: the region of your Secure Web Proxy instance, such as us-central1.
    • SWP_NAME: the name of your Secure Web Proxy instance.

  2. Import the Agent Gateway configuration:

    gcloud beta network-services agent-gateways import AGENT_GATEWAY_NAME \
   --source="my-agent-gateway.yaml" \
   --location=REGION \
   --project=PROJECT_ID

  3. Verify your Agent Gateway resource:

    gcloud beta network-services agent-gateways describe AGENT_GATEWAY_NAME \
   --location=REGION \
   --project=PROJECT_ID

    Confirm that the output displays your selfManaged configuration and the resource URI of your Secure Web Proxy instance before proceeding to the next section.

Configure Cloud Run ambient networking to access the Traffic Director API

When you configure a Cloud Run service with Direct VPC egress and --vpc-egress=all, all outbound connections from the container instance route through your VPC network. This includes the Envoy sidecar connection to trafficdirector.REGION.rep.googleapis.com.

To let the sidecar resolve and reach the Traffic Director API, configure a private Cloud DNS zone in your VPC network based on whether your environment uses VPC Service Controls:

Without VPC Service Controls

If your project doesn't use VPC Service Controls, create a private Cloud DNS zone that routes requests for trafficdirector.REGION.rep.googleapis.com to your Secure Web Proxy gateway IP address so Secure Web Proxy lets the traffic through:

  1. Retrieve the internal IP address of your Secure Web Proxy gateway:

    SWP_IP=$(gcloud network-services gateways describe SWP_NAME \
 --project="PROJECT_ID" \
 --location="REGION" \
 --format="value(addresses[0])")

    Replace the following:

    • SWP_NAME: the name of your Secure Web Proxy instance.
    • PROJECT_ID: your Google Cloud project ID.
    • REGION: the region of your deployment.

  2. Create a private Cloud DNS managed zone for the Traffic Director API:

    gcloud dns managed-zones create td-swp-zone \
 --project="PROJECT_ID" \
 --dns-name="trafficdirector.REGION.rep.googleapis.com." \
 --description="Private DNS zone routing control plane traffic to SWP" \
 --visibility="private" \
 --networks="VPC_NETWORK_NAME"

    Replace VPC_NETWORK_NAME with the name of your VPC network.

  3. Add an A record that points the Traffic Director API regional domain to your Secure Web Proxy IP address:

    gcloud dns record-sets create "trafficdirector.REGION.rep.googleapis.com." \
 --project="PROJECT_ID" \
 --zone="td-swp-zone" \
 --type="A" \
 --ttl=300 \
 --rrdatas="${SWP_IP}"

  4. Verify that the DNS record set is active in the private zone:

    gcloud dns record-sets list \
 --project="PROJECT_ID" \
 --zone="td-swp-zone"

    Confirm that the A record for trafficdirector.REGION.rep.googleapis.com. resolves to your Secure Web Proxy IP address.

With VPC Service Controls

For VPC Service Controls environments, provision a Private Service Connect regional endpoint targeting the regional Traffic Director API inside your VPC subnet and map the domain using a private Cloud DNS zone:

  1. Create a Private Service Connect regional endpoint targeting the regional Traffic Director API:

    gcloud network-connectivity regional-endpoints create td-rep-endpoint \
 --project="PROJECT_ID" \
 --region="REGION" \
 --network="projects/PROJECT_ID/global/networks/VPC_NETWORK_NAME" \
 --subnetwork="projects/PROJECT_ID/regions/REGION/subnetworks/VPC_SUBNET_NAME" \
 --target-google-api="trafficdirector.REGION.rep.googleapis.com"

    Replace the following:

    • PROJECT_ID: your Google Cloud project ID.
    • REGION: the region of your deployment.
    • VPC_NETWORK_NAME: the name of your VPC network.
    • VPC_SUBNET_NAME: the name of your VPC subnet.

  2. Retrieve the internal IP address of the regional endpoint:

    TD_ENDPOINT_IP=$(gcloud network-connectivity regional-endpoints describe td-rep-endpoint \
 --project="PROJECT_ID" \
 --region="REGION" \
 --format="value(address)")

  3. Create a private Cloud DNS managed zone for the Traffic Director API:

    gcloud dns managed-zones create td-psc-zone \
 --project="PROJECT_ID" \
 --dns-name="trafficdirector.REGION.rep.googleapis.com." \
 --description="Private DNS zone for regional endpoint" \
 --visibility="private" \
 --networks="VPC_NETWORK_NAME"

  4. Add an A record resolving the Traffic Director API regional domain to the regional endpoint IP address:

    gcloud dns record-sets create "trafficdirector.REGION.rep.googleapis.com." \
 --project="PROJECT_ID" \
 --zone="td-psc-zone" \
 --type="A" \
 --ttl=300 \
 --rrdatas="${TD_ENDPOINT_IP}"

  5. Verify your regional endpoint and DNS record set:

    gcloud dns record-sets list \
 --project="PROJECT_ID" \
 --zone="td-psc-zone"

    Confirm that the A record for trafficdirector.REGION.rep.googleapis.com. points to the regional endpoint IP address.

Deploy or update a Cloud Run service with ambient networking and Direct VPC egress

To connect your Cloud Run agent to the Secure Web Proxy instance in your VPC network, enable both Direct VPC egress and regional ambient networking, and configure the service with an Agent Identity. When you deploy with --functional-type=agent and --identity-type=agent-identity, Cloud Run grants roles/run.agentDefaultAccess, which includes roles/trafficdirector.client and roles/cloudtrace.agent permissions:

  1. Deploy a new Cloud Run agent service or update an existing service to enable regional ambient networking, Direct VPC egress for all outbound traffic, and Agent Identity:

    New service

    gcloud beta run deploy SERVICE_NAME \
 --image=IMAGE_URL \
 --network=VPC_NETWORK_NAME \
 --subnet=VPC_SUBNET_NAME \
 --vpc-egress=all \
 --functional-type=agent \
 --identity-type=agent-identity \
 --ambient-networking \
 --set-env-vars="GOOGLE_API_USE_CLIENT_CERTIFICATE=false,GOOGLE_API_USE_MTLS_ENDPOINT=never" \
 --region=REGION \
 --project=PROJECT_ID

    Existing service

    gcloud beta run services update SERVICE_NAME \
 --network=VPC_NETWORK_NAME \
 --subnet=VPC_SUBNET_NAME \
 --vpc-egress=all \
 --functional-type=agent \
 --identity-type=agent-identity \
 --ambient-networking \
 --update-env-vars="GOOGLE_API_USE_CLIENT_CERTIFICATE=false,GOOGLE_API_USE_MTLS_ENDPOINT=never" \
 --region=REGION \
 --project=PROJECT_ID

    Replace the following:

    • SERVICE_NAME: the name of your Cloud Run agent service.
    • IMAGE_URL: a reference to the container image, for example, us-docker.pkg.dev/cloudrun/container/hello:latest. If you use Artifact Registry, the repository REPO_NAME must already be created. The URL follows the format of LOCATION-docker.pkg.dev/PROJECT_ID/REPO_NAME/PATH:TAG .
    • VPC_NETWORK_NAME: the name of the VPC network that hosts your Secure Web Proxy instance. For information about creating a VPC network and subnet, see Create and manage VPC networks.
    • VPC_SUBNET_NAME: the name of the VPC subnet where your Secure Web Proxy instance is reachable.
    • REGION: the region of your service.
    • PROJECT_ID: your Google Cloud project ID.

  2. Verify that your Cloud Run service uses ambient networking, Direct VPC egress, and Agent Identity:

    gcloud beta run services describe SERVICE_NAME \
   --region=REGION \
   --project=PROJECT_ID

    Confirm that the output shows the Direct VPC egress subnet, all-traffic egress, regional ambient networking, and the assigned agent identity principal.

Configure your Cloud Run agent to trust Agent Gateway

For Secure Web Proxy to inspect HTTPS payloads and enforce policies, it must terminate outbound TLS sessions from your agent. Your Cloud Run agent container must trust the root or subordinate certificate authority (CA) certificate associated with your Secure Web Proxy TLS inspection policy in CA Service or your private enterprise PKI:

  1. Export the PEM-encoded CA certificate from the CA Service pool for your Secure Web Proxy instance:

    gcloud privateca pools get-ca-certs CA_POOL_NAME \
   --location=REGION \
   --project=PROJECT_ID \
   --output-file=agent-gateway-root.crt

    Replace the following:

    • CA_POOL_NAME: the name of the CA pool associated with your Secure Web Proxy TLS inspection policy.
    • REGION: the region of your CA pool.
    • PROJECT_ID: your Google Cloud project ID.

  2. Update your Cloud Run service to pass the certificate content in an environment variable:

    gcloud beta run services update SERVICE_NAME \
   --region=REGION \
   --project=PROJECT_ID \
   --update-env-vars="AGENT_GATEWAY_ROOT_CERT=$(cat agent-gateway-root.crt)"

    Replace the following:

    • SERVICE_NAME: the name of your Cloud Run agent service.
    • REGION: the region of your service.
    • PROJECT_ID: your Google Cloud project ID.
    Important: Your container's startup script or application code must read the AGENT_GATEWAY_ROOT_CERT environment variable and add the certificate to the system's or application's trust store. The exact steps depend on your base image and language runtime. For example, on Debian or Ubuntu base images, write the certificate to /usr/local/share/ca-certificates/agent-gateway.crt and run update-ca-certificates before starting your application. For Python or gRPC clients that bundle their own CA store, also set SSL_CERT_FILE, REQUESTS_CA_BUNDLE, and GRPC_DEFAULT_SSL_ROOTS_FILE_PATH to /etc/ssl/certs/ca-certificates.crt.

    For example, the following Debian or Ubuntu container entrypoint script, entrypoint.sh, installs AGENT_GATEWAY_ROOT_CERT into the system trust store and exports the CA bundle paths for Python and gRPC clients before starting your application:

    #!/usr/bin/env bash
set -e
if [ -n "${AGENT_GATEWAY_ROOT_CERT}" ]; then
 printf '%s\n' "${AGENT_GATEWAY_ROOT_CERT}" > /usr/local/share/ca-certificates/agent-gateway.crt
 update-ca-certificates
 export SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt
 export REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt
 export GRPC_DEFAULT_SSL_ROOTS_FILE_PATH=/etc/ssl/certs/ca-certificates.crt
fi
exec "$@"

  3. Verify that your service sets the AGENT_GATEWAY_ROOT_CERT environment variable:

    gcloud beta run services describe SERVICE_NAME \
   --region=REGION \
   --project=PROJECT_ID \
   --format="yaml(spec.template.spec.containers[0].env)"

Route egress traffic to Agent Gateway

After you configure your Cloud Run service and Agent Gateway, create a Network Services API EgressRouting policy to direct outbound traffic from your Cloud Run service to your Secure Web Proxy gateway:

  1. Create the EgressRouting resource:

    gcloud alpha network-services egress-routings create my-run-egress-routing \
   --location=REGION \
   --project=PROJECT_ID \
   --gateway="//networkservices.googleapis.com/projects/PROJECT_ID/locations/REGION/gateways/SWP_NAME" \
   --sources="workloadUri=//run.googleapis.com/projects/PROJECT_ID/locations/REGION/services/SERVICE_NAME"

    Replace the following:

    • REGION: the region of your Cloud Run service and gateway.
    • PROJECT_ID: your Google Cloud project ID.
    • SWP_NAME: the name of your underlying Secure Web Proxy Gateway resource, not the AgentGateway resource.
    • SERVICE_NAME: the name of your Cloud Run agent service. To route all Cloud Run services in the project through the gateway with a single policy, set workloadUri to //run.googleapis.com/projects/PROJECT_ID or //run.googleapis.com/projects/PROJECT_NUMBER.

    After EgressRouting takes effect, all outbound traffic from your Cloud Run service routes through Secure Web Proxy. Configure extension bindings and policies in the next section to govern outbound requests.

  2. Verify that the EgressRouting resource is active:

    gcloud alpha network-services egress-routings describe my-run-egress-routing \
   --location=REGION \
   --project=PROJECT_ID

    Confirm that sources lists your Cloud Run workload URI and gateway references your Secure Web Proxy gateway resource.

Configure policies on Agent Gateway

After you route egress traffic through Agent Gateway, govern your agent's outbound requests by attaching Service Extensions ExtensionBinding resources to your Agent Gateway resource:

  • Identity-based access control: Bind IAP with an ExtensionBinding resource and configure an IAM Unified Access Policy to control which agents can call specific Model Context Protocol (MCP) servers, tools, or endpoints.
  • Content security: Bind Model Armor with an ExtensionBinding resource to inspect and sanitize prompts and responses for prompt injection, sensitive data leakage, or policy violations.

When you attach an ExtensionBinding resource to your Agent Gateway resource, Secure Web Proxy passes outbound traffic to the attached extensions and ignores any GatewaySecurityPolicyRule resources on the underlying Secure Web Proxy Gateway (its TlsInspectionPolicy remains active). After you create or update an ExtensionBinding resource, changes can take up to five minutes to propagate to the gateway.

Configure IAP egress policies

Agent Gateway uses IAP as its policy decision engine to evaluate IAM Unified Access Policies. To enforce agent identity policies, define your access rules in an IAM Unified Access Policy and bind IAP to your gateway:

  1. Create an IAM Unified Access Policy using your Cloud Run service's Agent Identity principal, principal://agents.global.org-ORGANIZATION_ID.system.id.goog/resources/run/projects/PROJECT_NUMBER/locations/REGION/services/SERVICE_NAME, and bind the policy to your project or gateway by following Create IAM access policies and Bind a Unified Access Policy to a project.
  2. Bind IAP, iap.googleapis.com, to your Agent Gateway with an ExtensionBinding by following the instructions in Bind IAP to your Agent Gateway.
Note: Because --vpc-egress=all routes model calls such as Vertex AI at REGION-aiplatform.googleapis.com and aiplatform.googleapis.com through the gateway:
  • If you scope matchConditions in your IAP ExtensionBinding to prefix: "urn:mcp" (and optionally prefix: "urn:agent" for agent-to-agent traffic), model endpoints bypass IAP evaluation and work without additional IAP or Unified Access Policy rules.
  • If you omit matchConditions on your IAP ExtensionBinding, IAP evaluates all outbound traffic, so you must allow your model endpoint in your IAM Unified Access Policy (for example, destination.unregistered.host == 'REGION-aiplatform.googleapis.com' or destination.unregistered.host == 'aiplatform.googleapis.com'). For an example, see Create an agent-to-unregistered endpoint policy.

Configure Model Armor policies

To inspect and sanitize prompts and responses passing through your Agent Gateway, create Model Armor templates and bind them to your gateway:

  1. Create regional Model Armor request and response templates and grant the required roles to the Service Extensions service agent by following the instructions in Configure Model Armor on a gateway.
  2. Attach your templates to your Agent Gateway with an ExtensionBinding by following the instructions in Bind Model Armor for prompt and response sanitization.

Configure a centralized cross-project deployment with Shared VPC

In a multi-project organization, you can deploy your Cloud Run agents in one or more service projects while hosting an Agent Gateway, Secure Web Proxy instance, and Agent Registry in a dedicated networking host project using Shared VPC:

  • Project A, agent service project: Hosts the Cloud Run agent service and the local EgressRouting policy.
  • Project B, gateway and networking host project: Acts as the Shared VPC host project and must host the Agent Gateway, Secure Web Proxy instance, Agent Registry, ExtensionBinding resources, and IAM policy bindings.

Before starting these steps, enable run.googleapis.com, compute.googleapis.com, networkservices.googleapis.com, and trafficdirector.googleapis.com in Project A, along with aiplatform.googleapis.com if your agent calls Vertex AI. In Project B, deploy the Secure Web Proxy instance and Agent Gateway resource on the Shared VPC network as described in Create a self-managed Agent Gateway, and configure DNS or Private Service Connect routing as described in Configure Cloud Run ambient networking to access the Traffic Director API so ambient sidecars in Project A can reach the Traffic Director API.

To configure a cross-project deployment, complete the following steps:

  1. Configure Project B as a Shared VPC host project, attach Project A as a service project, and share the subnet that hosts your Secure Web Proxy instance. Enabling Shared VPC and attaching service projects requires roles/compute.xpnAdmin at the organization or folder level. For instructions, see Send traffic to a Shared VPC network with Direct VPC egress and Provision Shared VPC.

    Note: If a target MCP server or agent in a Shared VPC service project uses --ingress=internal, connect it to the Shared VPC network or add its project and Project B to the same VPC Service Controls perimeter. Otherwise, requests from Secure Web Proxy fail with 404 errors. For more information, see Special considerations for Shared VPC.

  2. In Project B, grant roles/compute.networkUser on the shared subnet to the Cloud Run service agent from Project A:

    gcloud compute networks subnets add-iam-policy-binding SHARED_SUBNET_NAME \
   --project=PROJECT_B_ID \
   --region=REGION \
   --member="serviceAccount:service-PROJECT_A_NUMBER@serverless-robot-prod.iam.gserviceaccount.com" \
   --role="roles/compute.networkUser"

    Replace the following:

    • SHARED_SUBNET_NAME: the name of the shared subnet in Project B.
    • PROJECT_B_ID: the project ID of Project B, the gateway and Shared VPC host project.
    • REGION: the region of the shared subnet.
    • PROJECT_A_NUMBER: the project number of Project A, the agent service project.

  3. Deploy the Cloud Run agent service in Project A pointing to the shared subnet in Project B:

    gcloud beta run deploy SERVICE_NAME \
   --project=PROJECT_A_ID \
   --image=IMAGE_URL \
   --subnet=projects/PROJECT_B_ID/regions/REGION/subnetworks/SHARED_SUBNET_NAME \
   --vpc-egress=all \
   --functional-type=agent \
   --identity-type=agent-identity \
   --ambient-networking \
   --set-env-vars="GOOGLE_API_USE_CLIENT_CERTIFICATE=false,GOOGLE_API_USE_MTLS_ENDPOINT=never" \
   --region=REGION

    Replace the following:

    • SERVICE_NAME: the name of your Cloud Run agent service in Project A.
    • PROJECT_A_ID: the project ID of Project A, the agent service project.
    • IMAGE_URL: a reference to the container image, for example, us-docker.pkg.dev/cloudrun/container/hello:latest. If you use Artifact Registry, the repository REPO_NAME must already be created. The URL follows the format of LOCATION-docker.pkg.dev/PROJECT_ID/REPO_NAME/PATH:TAG .

    After deploying the service, configure your agent in Project A to trust the root CA certificate of the Secure Web Proxy instance in Project B by following the steps in Configure your Cloud Run agent to trust Agent Gateway.

  4. Create an EgressRouting policy in Project A that references the Secure Web Proxy gateway in Project B. You must have roles/networkservices.admin in Project A:

    gcloud alpha network-services egress-routings create my-central-egress-routing \
   --location=REGION \
   --project=PROJECT_A_ID \
   --gateway="//networkservices.googleapis.com/projects/PROJECT_B_ID/locations/REGION/gateways/CENTRAL_SWP_NAME" \
   --sources="workloadUri=//run.googleapis.com/projects/PROJECT_A_ID/locations/REGION/services/SERVICE_NAME"

    Replace CENTRAL_SWP_NAME with the name of the Secure Web Proxy gateway in Project B. To route all Cloud Run services in Project A through Project B's gateway, set workloadUri to //run.googleapis.com/projects/PROJECT_A_ID or //run.googleapis.com/projects/PROJECT_A_NUMBER.

  5. Confirm that the cross-project EgressRouting resource is active in Project A:

    gcloud alpha network-services egress-routings describe my-central-egress-routing \
   --location=REGION \
   --project=PROJECT_A_ID

  6. Configure centralized IAP and Model Armor policies on the Agent Gateway resource in Project B as described in Configure policies on Agent Gateway:

    • To authorize the agent in Project A to call MCP servers registered in Project B, create an IAM Unified Access Policy in Project B whose principals list references Project A's project number, principal://agents.global.org-ORGANIZATION_ID.system.id.goog/resources/run/projects/PROJECT_A_NUMBER/locations/REGION/services/SERVICE_NAME, bind the policy to Project B or its Agent Gateway resource, and attach the IAP ExtensionBinding in Project B.
    • To apply centralized Model Armor guardrails in Project B, create your regional Model Armor templates, grant the required roles to Project B's Service Extensions service agent, and attach the Model Armor ExtensionBinding to the Agent Gateway resource in Project B.

Outbound agent interactions routed through Agent Gateway generate logs and distributed traces so that you can monitor policy decisions and debug agent behavior:

  • View request logs for your Cloud Run service and Secure Web Proxy gateway in Cloud Logging. For more information, see View and write container logs and Agent Gateway transaction log entries.
  • Analyze end-to-end request latency and traces across your agent and gateway in Cloud Trace. For more information, see Trace requests with Trace.

If outbound requests fail or bypass the gateway, see Troubleshoot Agent Gateway.

Supported regions

You can use Agent Gateway on Cloud Run in the following regions:

  • europe-west1
  • us-central1

Limitations

In addition to the ambient networking limitations and the Secure Web Proxy considerations in Deploy Secure Web Proxy as an Agent Gateway, the following limitations apply when you use Agent Gateway with Cloud Run:

  • Outbound agent requests routed through a TLS-inspecting Secure Web Proxy instance to *.mtls.googleapis.com and *.mtls.run.app endpoints fail with 503 errors because Secure Web Proxy terminates and re-originates TLS sessions without forwarding the client certificate.
  • Each regional self-managed Agent Gateway supports at most one regional Agent Registry in its registries list.
  • By default, each project supports up to 10 regional AgentGateway resources and 10 regional EgressRouting resources per region. New projects might start with a limit of 2 per region. To request a quota increase, contact your account team.
  • You must export the root or subordinate certificate from your CA Service pool or private enterprise PKI and configure your agent container to trust it.
  • You can't use Agent Gateway on the same source Cloud Run service as express links. Agent Gateway requires the regional ambient networking scope, while express links require the global scope.
