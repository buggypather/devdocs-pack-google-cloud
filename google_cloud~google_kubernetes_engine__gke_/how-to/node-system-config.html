Customizing node system configuration

This document shows you how to customize your Google Kubernetes Engine (GKE) node configuration by using a configuration file called a node system configuration.

A node system configuration is a configuration file that provides a way to adjust a limited set of system settings. In your node pool, you can use a node system configuration to specify custom settings for the kubelet Kubernetes node agent and for sysctl low-level Linux kernel configurations.

Caution: Changing the kubelet or sysctl settings can lead to unintended behavior that might negatively affect the health of your workloads and nodes. Extensively test any kubelet or sysctl changes before you deploy them on production workloads.

This document details the available configurations for a node system configuration and how to apply them to your GKE Standard node pools. Note that because GKE Autopilot clusters have a more managed node environment, their direct node system configuration options are limited compared to GKE Standard node pools.

Why use node system configurations

Node system configurations offer the following benefits:

  • Performance tuning: optimize network stack performance, memory management, CPU scheduling, or I/O behavior for demanding applications like AI training or serving, databases, high-traffic web servers, or latency-sensitive services.
  • Security hardening: apply specific kernel-level security settings or restrict certain system behaviors to reduce the attack surface.
  • Resource management: fine-tune how kubelet manages PIDs, disk space, image garbage collection, or CPU and memory resources.
  • Workload compatibility: help ensure that the node environment meets specific prerequisites for specialized software or older applications that require particular kernel settings.

Other options for customizing node configurations

You can also customize your node configuration by using other methods:

  • Runtime configuration file: to customize a containerd container runtime on your GKE nodes, you can use a different file called a runtime configuration file. For more information, see Customize containerd configuration in GKE nodes.
  • ComputeClass: you can specify node attributes in your GKE ComputeClass specification. You can use ComputeClasses, in both GKE Autopilot mode and Standard mode, in GKE version 1.32.1-gke.1729000 and later. For more information, see Customize the node system configuration.
  • DaemonSets: you can also use DaemonSets to customize nodes. For more information, see Automatically bootstrapping GKE nodes with DaemonSets.

Node system configurations are not supported in Windows Server nodes.

Before you begin

Before you begin, make sure to do the following:

  • Install command-line tools:
    • If you use the gcloud CLI examples in this document, ensure that you install and configure the Google Cloud CLI.
    • If you use the Terraform examples, ensure that you install and configure Terraform.
  • Grant permissions: you need appropriate IAM permissions to create and update GKE clusters and node pools, such as container.clusterAdmin or a different role with equivalent permissions.
  • Plan for potential workload disruption: custom node configurations are applied at the node pool level. Changes typically trigger a rolling update of the nodes in the pool, which involves re-creating the nodes. Plan for potential workload disruption and use Pod Disruption Budgets (PDBs) where appropriate.
  • Back up and test all changes: always test configuration changes in a staging or development environment before you apply them to production. Incorrect settings can lead to node instability or workload failures.
  • Review GKE default settings: GKE node images come with optimized default configurations. Only customize parameters if you have a specific need and understand the impact of your changes.

Add a node system configuration

You can customize your node system configuration by using either a ComputeClass or a configuration file.

Use a ComputeClass for node system configuration

You can use a custom ComputeClass to customize certain parameters in the kubelet and the Linux kernel. This method is available in GKE version 1.32.1-gke.1729000 and later.

To use a ComputeClass to customize your node system configuration, do the following:

  1. Create a ComputeClass that includes the spec.nodePoolAutoCreation.enabled: true field-value pair and specify the system configurations in the priorityDefaults field.
  2. Deploy a workload that selects the ComputeClass.

Create the ComputeClass

Write your ComputeClass configuration in YAML. Use the nodeSystemConfig field inside the priorityDefaults specification to set system configurations across all priorities.

The following example ComputeClass configures the static CPU manager policy and custom kernel parameters:

apiVersion: cloud.google.com/v1
kind: ComputeClass
metadata:
  name: custom-sysconfig
spec:
  nodePoolAutoCreation:
    enabled: true
  priorityDefaults:
    nodeSystemConfig:
      kubeletConfig:
        cpuManagerPolicy: static
      linuxNodeConfig:
        sysctls:
          net.core.somaxconn: 2048
  priorities:
  - machineFamily: n4

Apply the ComputeClass:

kubectl apply -f custom-sysconfig.yaml

Deploy a workload that selects the ComputeClass

In your Pod specification, add a node selector for the ComputeClass name:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      nodeSelector:
        cloud.google.com/compute-class: custom-sysconfig
      containers:
      - name: app-container
        image: nginx

Apply the workload:

kubectl apply -f my-app.yaml

For more information, see Customize the node system configuration.

Use a configuration file for node system configuration

When you use a node system configuration file, you use a YAML file that contains the configuration parameters for the kubelet and the Linux kernel. Although node system configurations are also available in GKE Autopilot mode, the steps in this document show you how to create and use a configuration file for GKE Standard mode.

To use a node system configuration file in GKE Standard mode, do the following:

  1. Create a configuration file. This file contains your kubelet and sysctl configurations.
  2. Add the configuration when you create a cluster or a node pool, or update an existing node pool.

Create a configuration file

Write your node system configuration in YAML. The following example adds configurations for the kubelet and sysctl options:

kubeletConfig:
  cpuManagerPolicy: static
  allowedUnsafeSysctls:
    - 'kernel.shm*'
    - 'kernel.msg*'
    - 'kernel.sem'
    - 'fs.mqueue.*'
    - 'net.*'
linuxConfig:
  sysctl:
    net.core.somaxconn: '2048'
    net.ipv4.tcp_rmem: '4096 87380 6291456'
  kernelOverrides:
    kernelCommandlineOverrides:
      specRstackOverflow: 'SPEC_RSTACK_OVERFLOW_OFF'
      initOnAlloc: 'INIT_ON_ALLOC_OFF'

In this example, the following applies:

  • The cpuManagerPolicy: static field configures the kubelet to use the static CPU management policy.
  • The net.core.somaxconn: '2048' field limits the socket listen() backlog to 2,048 bytes.
  • The net.ipv4.tcp_rmem: '4096 87380 6291456' field sets the minimum, default, and maximum value of the TCP socket receive buffer to 4,096 bytes, 87,380 bytes, and 6,291,456 bytes, respectively.
  • The kernelCommandlineOverrides block disables the speculative return stack overflow (SRSO) mitigation and the init_on_alloc kernel parameter.

If you want to add configurations only for the kubelet or sysctl, include only that section in your node system configuration. For example, to add a kubelet configuration, create the following file:

kubeletConfig:
  cpuManagerPolicy: static

For a complete list of the fields that you can add to your node system configuration, see the Kubelet configuration options and Sysctl configuration options sections.

Add the configuration to a Standard node pool

After you create the node system configuration, add the --system-config-from-file flag by using the Google Cloud CLI. You can add this flag when you create a cluster or a node pool, or when you update an existing node pool. You can't add a node system configuration by using the Google Cloud console.

Create a cluster with the node system configuration

You can add a node system configuration during cluster creation by using the gcloud CLI or Terraform. The following instructions apply the node system configuration to the default node pool:

gcloud CLI

gcloud container clusters create CLUSTER_NAME \
    --location=LOCATION \
    --system-config-from-file=SYSTEM_CONFIG_PATH

Replace the following:

  • CLUSTER_NAME: the name for your cluster
  • LOCATION: the compute zone or region of the cluster
  • SYSTEM_CONFIG_PATH: the path to the file that contains your kubelet and sysctl configurations

After you apply a node system configuration, the default node pool of the cluster uses the settings that you defined.

Terraform

To create a regional cluster with a customized node system configuration by using Terraform, refer to the following example:

resource "google_container_cluster" "default" {
  name     = "gke-standard-regional-cluster"
  location = "us-central1"

  initial_node_count = 1

  node_config {
    # Kubelet configuration
    kubelet_config {
      cpu_manager_policy = "static"
    }

    linux_node_config {
      # Sysctl configuration
      sysctls = {
        "net.core.netdev_max_backlog" = "10000"
      }

      # Linux cgroup mode configuration
      cgroup_mode = "CGROUP_MODE_V2"

      # Linux huge page configuration
      hugepages_config {
        hugepage_size_2m = "1024"
      }
    }
  }
}

For more information about using Terraform, see Terraform support for GKE.

Create a new node pool with the node system configuration

You can add a node system configuration when you use the gcloud CLI or Terraform to create a new node pool.

The following instructions apply the node system configuration to a new node pool:

gcloud CLI

gcloud container node-pools create POOL_NAME \
     --cluster CLUSTER_NAME \
     --location=LOCATION \
     --system-config-from-file=SYSTEM_CONFIG_PATH

Replace the following:

  • POOL_NAME: the name for your node pool
  • CLUSTER_NAME: the name of the cluster that you want to add a node pool to
  • LOCATION: the compute zone or region of the cluster
  • SYSTEM_CONFIG_PATH: the path to the file that contains your kubelet and sysctl configurations

Terraform

To create a node pool with a customized node system configuration by using Terraform, refer to the following example:

resource "google_container_node_pool" "default" {
  name    = "gke-standard-regional-node-pool"
  cluster = google_container_cluster.default.name

  node_config {
    # Kubelet configuration
    kubelet_config {
      cpu_manager_policy = "static"
    }

    linux_node_config {
      # Sysctl configuration
      sysctls = {
        "net.core.netdev_max_backlog" = "10000"
      }

      # Linux cgroup mode configuration
      cgroup_mode = "CGROUP_MODE_V2"

      # Linux huge page configuration
      hugepages_config {
        hugepage_size_2m = "1024"
      }
    }
  }
}

For more information about using Terraform, see Terraform support for GKE.

Update the node system configuration for an existing node pool

If you use a configuration file to manage the node system configuration, you can update an existing node pool in one of the following ways:

  • Non-disruptive live update: applies updated sysctl and kubelet settings directly to running nodes without re-creating the VMs or evicting Pods. Use this method when you're changing only sysctl or kubelet settings and want to minimize disruption.
  • Standard upgrade strategy: re-creates the nodes with the new configuration. Use this method when you're changing settings that don't support live updates, when your cluster or node pool runs a GKE version earlier than 1.37.1-gke.1954000, or when you want GKE to drain and reschedule your Pods onto new nodes.

To change the configuration of nodes that use a ComputeClass, see Edit a node system configuration for ComputeClasses instead.

Caution: With either method, including the kubeletConfig or linuxConfig section in your file replaces that entire section of the node pool's existing configuration. Any parameter that you omit from an included section is reset to its default value. During a live update, omitting a previously configured parameter that doesn't support live updates (such as cpuManagerPolicy or cgroupMode) causes GKE to reject the update. Before you update, get the existing node system configuration and include every setting that you want to keep.

You can apply updated sysctl and kubelet settings from your configuration file directly to running nodes. Because this process updates the parameters without re-creating or restarting the underlying VMs, it reduces disruption and speeds up the update. The following linuxConfig options still require the standard upgrade strategy:

  • Linux cgroup mode
  • Linux hugepages
  • Linux accurate time synchronization
  • Linux VFIO
  • Linux disk I/O scheduler

How live updates work

Live updates work as follows for each supported configuration:

  • sysctl configurations: GKE restarts the sysctl systemd service on each node to apply the kernel parameters in the linuxConfig.sysctl field. If you update a namespaced sysctl parameter, GKE also restarts the kubelet service to update the Pod-level sysctl configuration. For supported parameters, see Sysctl configuration options.
  • kubelet configurations: GKE restarts the kubelet service on each node to apply the parameters in the kubeletConfig field. Most kubelet configuration options support live updates. However, the cpuManagerPolicy, shutdownGracePeriodSeconds, and shutdownGracePeriodCriticalPodsSeconds options require the standard upgrade strategy.

In both cases, GKE applies the change in place on the running nodes without re-creating the VMs, evicting your Pods, or creating temporary surge VMs. GKE uses the sum of your node pool's --max-surge-upgrade and --max-unavailable-upgrade settings as the concurrency limit to determine how many existing nodes are updated in parallel.

Prerequisites for live updates

To use live updates, your cluster and node pool must meet the following prerequisites:

  • Run GKE version 1.37.1-gke.1954000 or later.
  • Enable the NodeReadinessController add-on on the cluster. During a live update, this controller temporarily applies the readiness.k8s.io/gke-node-live-update-reconciling:NoSchedule taint to each node being updated so that GKE doesn't schedule new Pods onto the node until the update completes:
    • For new clusters, include the NodeReadinessController add-on in the --addons flag during cluster creation. This flag enables only the add-ons that you specify and disables all others, so also include any default add-ons that you want to keep.
    • For existing clusters, pass the --update-addons=NodeReadinessController=ENABLED flag during a cluster update.

Apply a live update

To apply a live update, do the following:

  1. Create or modify your node system configuration YAML file so that contains the node pool's complete configuration, including the kubelet or sysctl settings that you want to change. To avoid resetting settings that you don't intend to change, start from the node pool's existing configuration.

  2. Update the node pool with your configuration file and set the value of the --node-config-update-mode flag to LIVE_UPDATE_WITHOUT_DRAIN:

    gcloud container node-pools update POOL_NAME \
    --cluster=CLUSTER_NAME \
    --location=LOCATION \
    --system-config-from-file=SYSTEM_CONFIG_PATH \
    --node-config-update-mode=LIVE_UPDATE_WITHOUT_DRAIN

    Replace the following:

    • POOL_NAME: the name of the node pool that you want to update
    • CLUSTER_NAME: the name of the cluster that contains the node pool
    • LOCATION: the compute zone or region of the cluster
    • SYSTEM_CONFIG_PATH: the path to the YAML file that contains your node system configuration

  3. Verify that GKE applied the updated settings to your node pool:

    gcloud container node-pools describe POOL_NAME \
    --cluster=CLUSTER_NAME \
    --location=LOCATION \
    --format="yaml(config.kubeletConfig, config.linuxNodeConfig)"

    The command output displays the active settings on the node pool in the config.kubeletConfig and config.linuxNodeConfig fields.

  4. Optional: restart your existing Pods. The live update doesn't interrupt running Pods, so GKE applies the updated settings only to Pods that start after the update completes. To apply the settings to a workload that is already running, restart its Pods, for example by running kubectl rollout restart on the Deployment.

If a live update doesn't go as expected, the recovery path depends on whether the update operation finished:

  • If the live update operation fails, see Recover from a failed live update.
  • If the live update operation succeeds but the new settings cause unintended workload behavior, see Revert a completed live update.

Recover from a failed live update

If a live update fails on a node, GKE stops the rollout immediately and leaves the node pool in a partially updated state. To inspect the failure details, do either of the following:

  • Run the gcloud container operations describe command. In the output, the statusMessage field identifies the node where the live update failed and the error that the node reported, for example:

    statusMessage: 'Failed precondition: live update failed on node gke-my-cluster-default-pool-ae3770ee-2kk0:
  Live update fails with error: failed to write new kubelet config: ...'

  • In the Logs Explorer, check for errors from the gke-node-live-update-reconciler component on the affected nodes.

Because a failed live update doesn't change the node pool's stored configuration, re-applying your previous configuration with the gcloud container node-pools update command doesn't trigger an update. After you inspect the failure, choose one of the following recovery options:

  • Fix the issue and complete the live update (recommended): resolve the issue that caused the failure, and then re-run the gcloud container node-pools update command from the previous procedure with your target configuration.
  • Revert to the previous configuration: if you can't resolve the issue, run the gcloud container node-pools rollback command to return the node pool to its previous configuration. Unlike a live update, this command re-creates all nodes in the node pool, which disrupts the workloads running on them.

Revert a completed live update

If a live update operation succeeds but a newly applied setting causes unintended workload behavior, revert the change in place by applying another live update with your previous configuration. This live update restores the previous configuration without evicting Pods or restarting nodes. The gcloud container node-pools rollback command isn't available after a successful operation; it works only when the operation fails.

To revert a completed live update, do the following:

  1. Update your node system configuration YAML file so that it contains the node pool's complete previous configuration. If a setting wasn't previously configured, set it explicitly to its default value rather than omitting it or leaving the section empty. For the default values, see Kubelet configuration options and Sysctl configuration options.

  2. Apply the previous configuration to your node pool:

    gcloud container node-pools update POOL_NAME \
    --cluster=CLUSTER_NAME \
    --location=LOCATION \
    --system-config-from-file=SYSTEM_CONFIG_PATH \
    --node-config-update-mode=LIVE_UPDATE_WITHOUT_DRAIN

Update by using the standard upgrade strategy

Use the standard upgrade strategy if you're updating configuration options that don't support live updates, if your cluster or node pool runs a GKE version earlier than 1.37.1-gke.1954000, or if you want GKE to automatically drain and reschedule your Pods onto newly created nodes.

To update an existing node pool by using the standard upgrade strategy, run the following command:

gcloud container node-pools update POOL_NAME \
    --cluster=CLUSTER_NAME \
    --location=LOCATION \
    --system-config-from-file=SYSTEM_CONFIG_PATH

Replace the following:

  • POOL_NAME: the name of the node pool that you want to update
  • CLUSTER_NAME: the name of the cluster that contains the node pool
  • LOCATION: the compute zone or region of the cluster
  • SYSTEM_CONFIG_PATH: the path to the YAML file that contains your node system configuration

This change requires re-creating the nodes, which can cause disruption to your running workloads. For more information about this specific change, find the corresponding row in the manual changes that re-create the nodes using a node upgrade strategy without respecting maintenance policies table.

For more information about node updates, see Planning for node update disruptions.

Caution: GKE immediately begins re-creating the nodes for this change by using the node upgrade strategy, regardless of active maintenance policies. GKE depends on resource availability for the change. Disabling node auto-upgrades doesn't prevent this change.

Edit a node system configuration

You can edit a node system configuration depending on whether you are using ComputeClasses or a configuration file.

For ComputeClasses

To edit the node system configuration when using ComputeClasses, choose one of the following methods:

Method 1: Update the existing ComputeClass

If you update the nodeSystemConfig in an existing ComputeClass, GKE applies the updated configuration to newly created nodes only. Existing nodes are not automatically updated.

To migrate your workloads to nodes with the new configuration, you can do one of the following:

  • Configure active migration in your ComputeClass.
  • To trigger a scale-up of new nodes, manually restart or re-create your workloads.

To update the ComputeClass, edit the YAML file and apply it:

kubectl apply -f custom-sysconfig.yaml

Method 2: Create a new ComputeClass

To help ensure that your workloads migrate to new nodes with the updated configuration, do the following:

  1. Create a new ComputeClass with a different name and the updated configuration.
  2. Update the node selector in your workload specifications to reference the new ComputeClass.
  3. Apply the updated workload specifications. The cluster autoscaler will provision new nodes with the new configuration and eventually scale down the old nodes.
  4. Delete the old ComputeClass object.

For configuration files

To edit a node system configuration when using a configuration file, you can create a new node pool with the configuration that you want, or update the node system configuration of an existing node pool.

Edit by creating a node pool

To edit a node system configuration by creating a node pool, do the following:

  1. Create a configuration file with the configuration that you want.
  2. Add the configuration to a new node pool.
  3. Migrate your workloads to the new node pool.
  4. Delete the old node pool.

Edit by updating an existing node pool

To change the node system configuration of an existing node pool in place, see Update the node system configuration for an existing node pool.

Get the existing node system configuration

To retrieve your node pool's existing node system configuration—for example, if you've already customized the configuration and want to add to it—use the gcloud container node-pools describe command. The output of the command lists any existing configurations under kubeletConfig and linuxNodeConfig.

Caution: When you update the Linux node configuration based on this output, you must specify the parameters under the linuxConfig field in the update command. The describe command shows these settings under linuxNodeConfig, but for updates, the correct field is linuxConfig. Using the output field linuxNodeConfig in an update request won't apply the changes.

For example, see the following snippet showing the output format from the describe command:

  kubeletConfig:
    allowedUnsafeSysctls:
    - kernel.shm*
    - kernel.msg*
    - kernel.sem
    - fs.mqueue.*
    - net.*
    cpuManagerPolicy: static
    insecureKubeletReadonlyPortEnabled: false
    maxParallelImagePulls: 2
  linuxNodeConfig: # IMPORTANT: Use linuxConfig when updating these settings
    sysctl:
      net.core.somaxconn: '2048'
      net.ipv4.tcp_rmem: 4096 87380 6291456

If you haven't already set a node system configuration, the output doesn't list kubeletConfig or linuxNodeConfig.

Reset the existing node system configuration

If you want to reset the node system configuration back to the defaults, update your configuration file with empty values for the kubelet and sysctl fields, for example:

```yaml
kubeletConfig: {}
linuxConfig:
  sysctl: {}
```

Delete a node system configuration

To remove a node system configuration, follow the steps depending on whether you are using ComputeClasses or a configuration file.

For ComputeClasses

To remove the custom node system configuration, do the following:

  1. Remove the cloud.google.com/compute-class node selector from your workload specifications.
  2. Apply the updated workload specifications. GKE re-creates the workloads on default nodes. The cluster autoscaler will eventually scale down and delete the nodes that were provisioned for the ComputeClass.

  3. Delete the ComputeClass object from the cluster:

    kubectl delete computeclass CUSTOM_COMPUTE_CLASS_NAME

For configuration files

To remove a node system configuration that was applied using a configuration file, do the following:

  1. Create a new node pool without the configuration file.
  2. Migrate your workloads to the new node pool.
  3. Delete the node pool that has the old node system configuration.

Configuration options for the kubelet

The tables in this section describe the kubelet options that you can modify.

CPU management

The following table describes the CPU management options for the kubelet.

kubelet config settings Restrictions Default setting Description
cpuCFSQuota Must be true or false. true This setting enforces the Pod's CPU limit. Setting this value to false means that the CPU limits for Pods are ignored.

Ignoring CPU limits might be beneficial in certain scenarios where Pods are sensitive to CPU limits. The risk of disabling cpuCFSQuota is that a rogue Pod can consume more CPU resources than intended.
cpuCFSQuotaPeriod Must be a duration of time. "100ms" This setting sets the CPU CFS quota period value, cpu.cfs_period_us, which specifies the period of how often a cgroup's access to CPU resources should be reallocated. This option lets you tune the CPU throttling behavior.
reservedSystemCPUs (Preview) Must be a list of specific CPU cores to reserve (for example, 0-1 or 0,1 to reserve cores 0 and 1). Because cores are zero-indexed, the values must be less than the number of vCPUs on the machine type. none

Explicitly reserves specific CPU cores for host system services, such as OS daemons and the kubelet service. By default, these services can run on any CPU core, which can cause performance issues for CPU-sensitive workloads. While the cpuManagerPolicy: static setting assigns dedicated cores to Guaranteed Pods with integer CPU requests, it doesn't prevent host system services from using those cores. Adding the reservedSystemCPUs setting confines host system services to their own reserved cores, preventing them from interrupting your workloads' exclusive cores. To do this task, GKE automatically pins the system.slice cgroup to the reserved cores at node startup.

Reserving system CPUs reduces the overall allocatable capacity of your nodes. While Burstable and BestEffort Pods can still run on these reserved cores, their CPU requests, including fractional requests from GKE DaemonSets, still count against the node's allocatable capacity. Because exclusive Guaranteed workloads require whole cores, even small fractional requests reduce the number of exclusive cores available.

Ensure that you reserve sufficient CPU cores in reservedSystemCPUs. If you reserve too few cores, host system daemons and OS processes might become CPU-constrained under high load, which can cause instability or dropped network packets.

Memory management and eviction

The following table describes the modifiable options for memory management and eviction. This section also contains a separate table that describes the modifiable options for the evictionSoft flag.

kubelet config settings Restrictions Default setting Description
evictionSoft Map of signal names. For value restrictions, see the following table. none This setting maps signal names to a quantity or percentage that defines soft eviction thresholds. A soft eviction threshold must have a grace period. The kubelet does not evict Pods until the grace period is exceeded.
evictionSoftGracePeriod Map of signal names. For each signal name, the value must be a positive duration less than 5m. Valid time units are ns, us (or µs), ms, s, or m. none This setting maps signal names to durations that define grace periods for soft eviction thresholds. Each soft eviction threshold must have a corresponding grace period.
evictionMinimumReclaim Map of signal names. For each signal name, the value must be a positive percentage less than 10%. none This setting maps signal names to percentages that define the minimum amount of a given resource that the kubelet reclaims when it performs a Pod eviction.
evictionMaxPodGracePeriodSeconds Value must be an integer between 0 and 300. 0 This setting defines, in seconds, the maximum grace period for Pod termination during eviction.
singleProcessOOMKill Value must be true or false. true for cgroupv1 nodes, false for cgroupv2 nodes. This setting sets whether the processes in the container are OOMkilled individually or as a group.

Available on GKE versions 1.32.4-gke.1132000, 1.33.0-gke.1748000 or later.

kubelet config settings Restrictions Default setting Description
memoryAvailable Value must be a quantity greater than 100Mi and less than 50% of the node's memory. none This setting represents the amount of memory available before soft eviction. Defines the amount of the memory.available signal in the kubelet .
nodefsAvailable Value must be between 10% and 50%. none This setting represents the nodefs available before soft eviction. Defines the amount of the nodefs.available signal in the kubelet .
nodefsInodesFree Value must be between 5% and 50%. none This setting represents the nodefs inodes that are free before soft eviction. Defines the amount of the nodefs.inodesFree signal in the kubelet .
imagefsAvailable Value must be between 15% and 50%. none This setting represents the imagefs available before soft eviction. Defines the amount of imagefs.available signal in the kubelet .
imagefsInodesFree Value must be between 5% and 50%. none This setting represents the imagefs inodes that are free before soft eviction. Defines the amount of the imagefs.inodesFree signal in the kubelet.
pidAvailable Value must be between 10% and 50%. none This setting represents the PIDs available before soft eviction. Defines the amount of the pid.available signal in the kubelet.

PID management

The following table describes the modifiable options for PID management.

kubelet config settings Restrictions Default setting Description
podPidsLimit Value must be between 1024 and 4194304. none This setting sets the maximum number of process IDs (PIDs) that each Pod can use.

Logging

The following table describes the modifiable options for logging.

kubelet config settings Restrictions Default setting Description
containerLogMaxSize Value must be a positive number and a unit suffix between 10Mi and 500Mi, inclusive. 10Mi This setting controls the containerLogMaxSize setting of container log rotation policy, which lets you configure the maximum size for each log file. The default value is 10Mi. Valid units are Ki, Mi, and Gi.
containerLogMaxFiles Value must be an integer between 2 and 10, inclusive. 5 This setting controls the containerLogMaxFiles setting of the container log files rotation policy, which lets you configure the maximum number of files allowed for each container respectively. The default value is 5. The total log size (container_log_max_size*container_log_max_files) per container can't exceed 1% of the total storage of the node.

Image garbage collection

The following table describes the modifiable options for image garbage collection.

Linux cgroup mode configuration options

Caution: GKE deprecates cgroupv1 with minor version 1.31, and removes support for cgroupv1 with version 1.35. For more information about how GKE is transitioning to cgroupv2 and how you can prepare your clusters for this transition, see Migrate nodes to Linux cgroupv2.

The container runtime and kubelet use Linux kernel cgroups for resource management, such as limiting how much CPU or memory each container in a Pod can access. There are two versions of the cgroup subsystem in the kernel: cgroupv1 and cgroupv2. Kubernetes support for cgroupv2 was introduced as alpha in Kubernetes version 1.18, beta in 1.22, and GA in 1.25. For more information, see the Kubernetes cgroups v2 documentation.

Node system configuration lets you customize the cgroup configuration of your node pools. You can use cgroupv1 or cgroupv2. GKE uses cgroupv2 for new Standard node pools that run version 1.26 and later, and cgroupv1 for node pools that run versions earlier than 1.26. For node pools that were created with node auto-provisioning, the cgroup configuration depends on the initial cluster version, not the node pool version. cgroupv1 is not supported on Arm machines.

You can use node system configuration to change the setting for a node pool to use cgroupv1 or cgroupv2 explicitly. Upgrading an existing node pool that uses cgroupv1 to version 1.26 doesn't change the setting to cgroupv2. Existing node pools that run a version earlier than 1.26—and that don't include a customized cgroup configuration—will continue to use cgroupv1. To change the setting, you must explicitly specify cgroupv2 for the existing node pool.

For example, to configure your node pool to use cgroupv2, use a node system configuration file such as the following:

linuxConfig:
  cgroupMode: 'CGROUP_MODE_V2'

The supported cgroupMode options are the following:

  • CGROUP_MODE_V1: use cgroupv1 on the node pool.
  • CGROUP_MODE_V2: use cgroupv2 on the node pool.
  • CGROUP_MODE_UNSPECIFIED: use the default GKE cgroup configuration.

To use cgroupv2, the following requirements and limitations apply:

  • For a node pool that runs a version earlier than 1.26, you must use gcloud CLI version 408.0.0 or later. Alternatively, use gcloud beta with version 395.0.0 or later.
  • Your cluster and node pools must run GKE version 1.24.2-gke.300 or later.
  • You must use either the Container-Optimized OS with containerd or Ubuntu with containerd node image.
  • If any of your workloads depend on reading the cgroup filesystem (/sys/fs/cgroup/...), ensure that they are compatible with the cgroupv2 API.
  • If you use any monitoring or third-party tools, ensure that they are compatible with cgroupv2.
  • If you use Java workloads (JDK), we recommend that you use versions which fully support cgroupv2, including JDK 8u372, JDK 11.0.16 or later, or JDK 15 or later.

When you add a node system configuration, GKE must re-create the nodes to implement the changes. After you add the configuration to a node pool and the nodes are re-created, you can verify the new configuration.

You can verify the cgroup configuration for nodes in a node pool by using gcloud CLI or the kubectl command-line tool:

  • EFFECTIVE_CGROUP_MODE_V2: the nodes use cgroupv2

Linux hugepages configuration options

You can use manually pre-allocated hugepages or automatically assigned transparent hugepages.

Pre-allocated hugepages

You can use a node system configuration file to pre-allocate hugepages. Kubernetes supports pre-allocated hugepages as a resource type, similar to CPU or memory.

To use hugepages, the following limitations and requirements apply:

  • To ensure that the node is not fully occupied by hugepages, the overall size of the allocated hugepages can't exceed either the following:
    • On machines with less than 30 GB memory: 60% of the total memory. For example, on e2-standard-2 machine with 8 GB of memory, you can't allocate more than 4.8 GB for hugepages.
    • On machines with more than 30 GB memory: 80% of the total memory. For example, on c4a-standard-8 machines with 32 GB of memory, hugepages cannot exceed 25.6 GB.
  • 1 GB hugepages are only available on A3, C2D, C3, C3D, C4, C4A, C4D, C4N, CT5E, CT5LP, CT6E, H3, M2, M3, M4, Z3, or Z4D machine types.

true or false false This setting enables accurate time synchronization. This feature is only supported with specific machine types, operating systems, and zones.

After you enable accurate time synchronization, GKE collects and exports the following information:

  • The compute.googleapis.com/instance/clock_accuracy/ptp_kvm/nanosecond_accuracy metric, which indicates the VM host clock accuracy to UTC.
  • The projects/PROJECT_ID/logs/chrony.tracking log, which contains the tracking logs from chrony. These logs provide information such as the gain or loss rate of the system clock.

You can use this information to create log-based metrics and dashboards in Cloud Monitoring to analyze the performance and reliability of the time synchronization.

For example, the following gke-clock-metric.json configuration defines a log-based metric of the maximum host clock error:

{
  "name": "phc-clock-max-error",
  "description": "Maximum error of the VM clock from the host clock exposed by ptp_kvm",
  "filter": "resource.type=\"k8s_node\" AND log_id(\"chrony.tracking\")",
  "metricDescriptor": {
    "metricKind": "DELTA",
    "valueType": "DISTRIBUTION",
    "unit": "s",
    "labels": []
  },
  "valueExtractor": "REGEXP_EXTRACT(textPayload, \"^.*PHC0.* ([-\\\\d\\\\.eE]+)$\")",
  "bucketOptions": {
    "explicitBuckets": {
      "bounds": [
        0.0, 5.0E-7, 1.0E-6, 2.0E-6, 4.0E-6, 5.0E-6, 8.0E-6, 1.0E-5, 2.0E-5,
        1.0E-4, 0.001, 0.01, 0.1, 1.0
      ]
    }
  }
}

Linux VFIO configuration options

The following table describes the parameter to configure VFIO (Virtual Function I/O) on a node. VFIO allows safe, unprivileged, userspace drivers to access I/O devices.

Config parameter Restrictions Default value Description
nodeVfioConfig.dmaEntryLimit Must be an integer between 65535 and 4194304. 65535 Specifies the maximum number of DMA entries (pages) that can be mapped by the VFIO IOMMU type 1 driver for a container. This limit affects the total amount of host memory that can be pinned for direct device access, which is often critical for high-performance devices like TPUs and GPUs. This setting corresponds to the following kernel parameter: /sys/module/vfio_iommu_type1/parameters/dma_entry_limit. Higher values might be needed for workloads mapping large memory regions.

Available on GKE versions 1.36.0-gke.3009000 or later.

Linux disk I/O scheduler configuration options

The following table describes the parameters to configure the disk I/O scheduler for node pools.

Config parameter Supported values Default value Description
diskIoScheduler.nodeSystemIoScheduler mq-deadline, bfq, kyber, none bfq for Container-Optimized OS image, none for Ubuntu image Configures the I/O scheduler for the boot disk or ephemeral local SSD that runs node system workloads.

Available on GKE versions 1.36.0-gke.3009000 or later.
diskIoScheduler.nodeAttachedDiskIoScheduler mq-deadline, bfq, kyber, none none Configures the I/O scheduler for the attached disks.

Available on GKE versions 1.36.0-gke.3009000 or later.

Linux kernel override options

You can use a node system configuration file to override specific Linux kernel parameters, including the kernel command line and Multi-Gen LRU settings. These settings are supported for clusters running GKE versions 1.35.0-gke.1018000 or later.

Linux kernel command-line options

The following table describes the modifiable kernel command-line options.

Config parameter Supported values Description
specRstackOverflow SPEC_RSTACK_OVERFLOW_OFF Changes the speculative return stack overflow (SRSO) mitigation. The only supported value is SPEC_RSTACK_OVERFLOW_OFF.
initOnAlloc INIT_ON_ALLOC_OFF Changes the init_on_alloc parameter in the kernel command line. The only supported value is INIT_ON_ALLOC_OFF.

Multi-Gen LRU configuration options

The following table describes the modifiable Multi-Gen LRU options.

Config parameter Supported values Description
enabled true, false Enables or disables the Multi-Gen LRU. This setting configures the kill switch.
minTtlMs Positive integer Optional. Configures the min_ttl_ms thrashing prevention value for Multi-Gen LRU.

OS file configuration options

You can use a node system configuration file to add entries to specific OS configuration files on your nodes. These settings are supported for clusters running GKE versions 1.35.0-gke.1018000 or later.

Additional /etc/hosts entries

This field adds /etc/hosts file entries, such as in the following example:

linuxConfig:
  additionalEtcHosts:
    - ip: 1.2.3.4
      host: myownpersonaldomain.com
    - ip: 5.6.7.8
      host: otherpersonaldomain.com

Additional /etc/systemd/resolved.conf entries

This field adds /etc/systemd/resolved.conf file entries. This field accepts an array of key-value pairs. The following keys are supported:

  • DNS
  • FallbackDNS
  • Domains
  • LLMNR
  • MulticastDNS
  • DNSSEC
  • DNSOverTLS
  • Cache
  • CacheFromLocalhost
  • DNSStubListener
  • DNSStubListenerExtra
  • ReadEtcHosts
  • ResolveUnicastSingleLabel
  • StaleRetentionSec

The following example adds two DNS server values (8.8.8.8 and 8.8.4.4) to the DNS key and a domain value (myownpersonaldomain.com) to the Domains key:

linuxConfig:
  additionalEtcSystemdResolvedConf:
    - key: DNS
      value:
        - 8.8.8.8
        - 8.8.4.4
    - key: Domains
      value:
        - myownpersonaldomain.com

Additional /etc/resolv.conf entries

This field adds /etc/resolv.conf file entries. This field accepts an array of key-value pairs. The following keys are supported:

  • nameserver
  • search
  • sortlist
  • options

The following example adds a DNS server value (1.1.1.1) to the nameserver key and a domain value (myownpersonaldomain.com) to the search key:

linuxConfig:
  additionalEtcResolvConf:
    - key: nameserver
      value:
        - 1.1.1.1
    - key: search
      value:
        - myownpersonaldomain.com

Time zone configuration

The timeZone field sets the time zone on the node, for example, America/Los_Angeles. This setting is supported for clusters running GKE versions 1.35.0-gke.1018000 or later.

The following example sets the timeZone field to America/Los_Angeles:

linuxConfig:
  timeZone: America/Los_Angeles
