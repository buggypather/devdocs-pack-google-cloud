Configure sandboxes for services

Preview — Cloud Run sandboxes

This feature is subject to the "Pre-GA Offerings Terms" in the General Service Terms section of the Service Specific Terms. Pre-GA features are available "as is" and might have limited support. For more information, see the launch stage descriptions.

Cloud Run sandboxes provide a fast, secure, and isolated environment to execute untrusted code or run tools, such as AI agents, within your existing service in the second-generation environment. Sandboxes are highly optimized for latency and run within the same instance as your container, sharing its allocated CPU and memory.

This page describes how to configure sandboxes on your container. For details about writing code to interact with the sandbox using the CLI, see Code execution in Cloud Run.

Enable sandboxes

Any configuration change leads to the creation of a new revision. Subsequent revisions will also automatically get this configuration setting unless you make explicit updates to change it.

When you enable sandboxes, your Cloud Run service deploys in the second-generation execution environment. To enable sandboxes in Cloud Run services, use the Google Cloud CLI, a YAML configuration, or Terraform:

gcloud

To deploy or update the service, specify the --sandbox-launcher flag:

  • To deploy a new service, run the following command:

    gcloud beta run deploy SERVICE --image IMAGE_URL --sandbox-launcher

    Replace the following:

    • SERVICE: the name of your Cloud Run service.
    • IMAGE_URL: a reference to the container image, for example, us-docker.pkg.dev/cloudrun/container/hello:latest. If you use Artifact Registry, the repository REPO_NAME must already be created. The URL follows the format of LOCATION-docker.pkg.dev/PROJECT_ID/REPO_NAME/PATH:TAG

  • To update an existing service, run the following command:

    gcloud beta run services update SERVICE --sandbox-launcher

YAML

  1. If you are creating a new service, skip this step. If you are updating an existing service, download its YAML configuration:

    gcloud run services describe SERVICE --format export > service.yaml

  2. Update your YAML file to include the sandboxLauncher attribute set to true inside your container configuration:

    apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: SERVICE
  annotations:
    run.googleapis.com/launch-stage: BETA
spec:
  template:
    spec:
      containers:
      - name: CONTAINER
        image: IMAGE_URL
        sandboxLauncher: true
        port: 8080

    Replace the following:

    • SERVICE: the name of your Cloud Run service.
    • CONTAINER: the name of your container.
    • IMAGE_URL: a reference to the container image, for example, us-docker.pkg.dev/cloudrun/container/hello:latest. If you use Artifact Registry, the repository REPO_NAME must already be created. The URL follows the format of LOCATION-docker.pkg.dev/PROJECT_ID/REPO_NAME/PATH:TAG

  3. Create or update the service using the following command:

    gcloud run services replace service.yaml

    The gcloud run services replace command defaults to using service.yaml file if present.

Terraform

To learn how to apply or remove a Terraform configuration, see Basic Terraform commands.

Add the following to a google_cloud_run_v2_service resource in your Terraform configuration:
resource "google_cloud_run_v2_service" "default" {
  name     = "SERVICE"
  location = "REGION"

  template {
    containers {
      image            = "IMAGE_URL"
      sandbox_launcher = true
      ports {
        container_port = 8080
      }
    }
  }
}

Replace the following:

  • SERVICE: the name of your Cloud Run service.
  • REGION: the Google Cloud region. For example, europe-west1.
  • IMAGE_URL: a reference to the container image, for example, us-docker.pkg.dev/cloudrun/container/hello:latest. If you use Artifact Registry, the repository REPO_NAME must already be created. The URL follows the format of LOCATION-docker.pkg.dev/PROJECT_ID/REPO_NAME/PATH:TAG

Sandboxes share the CPU and memory allocated to the host container. Make sure your main container's CPU and memory limits can accommodate both your application and any active sandboxes that you run at the same time.

Configure sandbox templates

Sandbox templates let you define container images for sandboxes. Instead of running sandbox sessions inside your main application container, the sandbox do --template and sandbox run --template commands launch new containers using your specified images, such as Python, Node.js, or a custom execution environment. These sandboxes run in their own containers and share the CPU and memory limits of the main container. You can't set separate CPU and memory limits for a template. Cloud Run supports up to 10 sandbox templates. Volume mounts must reference an in-memory volume on your Cloud Run resource. Sandbox templates provide the following capabilities:

  • Dedicated container images: Declare distinct container images, such as python:3.12-slim or busybox:latest, as sandbox templates. You can also use other runtimes and tools for sandboxes that aren't required on your main container. This keeps your main container lightweight by isolating tools and runtimes used only for sandboxing.

  • On-demand instantiation: The sandbox CLI (/usr/local/gcp/bin/sandbox) spawns new sandbox containers from a template without provisioning new VMs or billing for new instances.

  • Isolated file sharing per sandbox: Share an in-memory volume between your main container and multiple sandboxes while restricting each sandbox to its own isolated subdirectory to prevent sandboxes from viewing or modifying other files.

You can configure sandbox templates using a YAML configuration or the Cloud Run Admin API:

YAML

  1. If you are creating a new service, skip this step. If you are updating an existing service, download its YAML configuration:

    gcloud run services describe SERVICE --format export > service.yaml

  2. Update your service YAML file to include the sandboxes templates configuration:

    apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: SERVICE
  annotations:
    run.googleapis.com/launch-stage: BETA
spec:
  template:
    spec:
      containers:
      - image: IMAGE_URL
        ports:
        - containerPort: 8080
        sandboxLauncher: true
        volumeMounts:
        - name: VOLUME_NAME
          mountPath: CONTAINER_MOUNT_PATH
      volumes:
      - name: VOLUME_NAME
        emptyDir:
          medium: Memory
      sandboxes:
        templates:
        - name: TEMPLATE_NAME
          image: TEMPLATE_IMAGE_URL
          volumeMounts:
          - name: VOLUME_NAME
            mountPath: SANDBOX_MOUNT_PATH
            subPath: SUBPATH

    Replace the following:

    • SERVICE: the name of your Cloud Run service.
    • IMAGE_URL: the container image URL to use for the main container.
    • TEMPLATE_NAME: the name of the template.
    • TEMPLATE_IMAGE_URL: the container image URL to use for the sandbox template.
    • Optional: VOLUME_NAME: the name of the volume to mount.
    • Optional: CONTAINER_MOUNT_PATH: the path where the volume is mounted inside the main container.
    • Optional: SANDBOX_MOUNT_PATH: the path where the volume is mounted inside the sandbox container.
    • Optional: SUBPATH: a relative subdirectory path within the volume to mount into the sandbox container, such as my-subdir. To set a different subdirectory for each sandbox at runtime, use a $(VARIABLE_NAME) placeholder, such as $(SANDBOX_DIR):
      • VARIABLE_NAME can contain only ASCII letters and underscores; digits and hyphens aren't supported.
      • To resolve the placeholder at runtime, pass the --template-var=VARIABLE_NAME=VALUE flag along with --template.
      • subPath doesn't create directories automatically. Create the resolved SUBPATH directory in the volume from the main container, for example using mkdir -p, before running sandbox do or sandbox run.

  3. Create or update the service using the following command:

    gcloud run services replace service.yaml

    The gcloud run services replace command defaults to using service.yaml file if present.

REST API

To configure sandbox templates, send a PATCH request to the Cloud Run Admin API:

curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
-H "Content-Type: application/json" \
-X PATCH \
"https://run.googleapis.com/v2/projects/PROJECT_ID/locations/REGION/services/SERVICE?updateMask=launchStage,template.containers,template.sandboxes,template.volumes" \
-d '{
  "launchStage": "BETA",
  "template": {
    "containers": [
      {
        "image": "IMAGE_URL",
        "sandboxLauncher": true,
        "volumeMounts": [
          {
            "name": "VOLUME_NAME",
            "mountPath": "CONTAINER_MOUNT_PATH"
          }
        ]
      }
    ],
    "sandboxes": {
      "templates": [
        {
          "name": "TEMPLATE_NAME",
          "image": "TEMPLATE_IMAGE_URL",
          "volumeMounts": [
            {
              "name": "VOLUME_NAME",
              "mountPath": "SANDBOX_MOUNT_PATH",
              "subPath": "SUBPATH"
            }
          ]
        }
      ]
    },
    "volumes": [
      {
        "name": "VOLUME_NAME",
        "emptyDir": {
          "medium": "MEMORY"
        }
      }
    ]
  }
}'

Replace the following:

  • SERVICE: the name of your Cloud Run service.
  • PROJECT_ID: your Google Cloud project ID.
  • REGION: the region where your Cloud Run resource is deployed.
  • IMAGE_URL: the container image URL to use for the main container.
  • TEMPLATE_NAME: the name of the template.
  • TEMPLATE_IMAGE_URL: the container image URL to use for the sandbox template.
  • Optional: VOLUME_NAME: the name of the volume to mount.
  • Optional: CONTAINER_MOUNT_PATH: the path where the volume is mounted inside the main container.
  • Optional: SANDBOX_MOUNT_PATH: the path where the volume is mounted inside the sandbox container.
  • Optional: SUBPATH: a relative subdirectory path within the volume to mount into the sandbox container, such as my-subdir. To set a different subdirectory for each sandbox at runtime, use a $(VARIABLE_NAME) placeholder, such as $(SANDBOX_DIR):
    • VARIABLE_NAME can contain only ASCII letters and underscores; digits and hyphens aren't supported.
    • To resolve the placeholder at runtime, pass the --template-var=VARIABLE_NAME=VALUE flag along with --template.
    • subPath doesn't create directories automatically. Create the resolved SUBPATH directory in the volume from the main container, for example using mkdir -p, before running sandbox do or sandbox run.
