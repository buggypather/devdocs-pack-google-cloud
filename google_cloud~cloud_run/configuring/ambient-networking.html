Configure ambient networking

Preview — Ambient networking

This feature is subject to the "Pre-GA Offerings Terms" in the General Service Terms section of the Service Specific Terms. Pre-GA features are available "as is" and might have limited support. For more information, see the launch stage descriptions.

Ambient networking brings a simplified resource networking experience built into Cloud Run. It gives your resources a fully managed data plane to remove the operational burden of building and maintaining custom proxies. It also abstracts service mesh concepts, so you get advanced networking features without learning or configuring a mesh.

When you enable ambient networking, traffic passes through unchanged by default so that your existing HTTP and TCP traffic continues to work. Enabling ambient networking on its own doesn't change how your resource behaves. As a foundation, ambient networking lets you opt in to the capabilities described in the following section.

Use cases

Ambient networking is the foundation for advanced networking capabilities in Cloud Run. After you enable ambient networking, you can opt in to the following features:

  • Agent Gateway on Cloud Run: govern agent traffic with access and security policies that your organization manages centrally.
  • Express links: route traffic to other Cloud Run services. The ambient sidecar injects the right credentials for you, so you can call a destination over plain HTTP and remove authentication code from your application.

Architecture

Ambient networking runs a fully managed Envoy sidecar container inside each container instance of your Cloud Run resource, alongside your application container. The sidecar intercepts the instance's network traffic and applies the routing and security policy that Cloud Run distributes to it.

Note: The sidecar is fully managed by Google Cloud. You don't deploy, configure, or access it, and you don't need to define any service mesh resources. Because the sidecar shares your container instance's CPU and memory, you must increase your resource limits before you enable ambient networking.

Ambient networking scopes

Ambient networking supports a global scope and a regional scope. The scope determines whether the sidecar connects to a global or regional routing plane:

  • Regional (default): Cloud Run connects the sidecar to a regional routing plane, limiting routing and security policies to destinations within your service's region. This scope supports data residency (DRZ) requirements for data at rest, in use, and in transit. If you don't specify a scope, ambient networking uses the regional scope.
  • Global: Cloud Run connects the sidecar to a global routing plane, allowing it to route traffic to destinations in any region.

Each feature that uses ambient networking requires a specific scope:

Feature Global scope Regional scope
Agent Gateway on Cloud Run Not supported Supported
Express links Supported Not supported

Limitations

The following limitations apply to ambient networking:

  • UDP traffic isn't supported. Ambient networking only supports HTTP and TCP traffic.
  • Inbound requests don't support end-to-end HTTP/2. For details, see Known issues.
  • The regional scope doesn't support VPC networks that resolve *.googleapis.com to Private Google Access IP addresses. For details, see Known issues.
  • The first generation execution environment isn't supported. If you don't specify an execution environment, Cloud Run uses the second generation.
  • Container instances take longer to start. For details, see Known issues.

Required roles

To get the permissions that you need to configure and deploy Cloud Run services, ask your administrator to grant you the following IAM roles:

  • Cloud Run Developer (roles/run.developer) on the Cloud Run service
  • Service Account User (roles/iam.serviceAccountUser) on the service identity

If you are deploying a service or function from source code, you must also have additional roles granted to you on your project and Cloud Build service account.

The Cloud Run resource's service identity must also have the following roles:

  • Traffic Director Client (roles/trafficdirector.client)
  • Cloud Trace Agent (roles/cloudtrace.agent)

To grant these roles to the service identity, use gcloud:

gcloud projects add-iam-policy-binding PROJECT_ID \
    --member="serviceAccount:RUN_CLIENT_SA@PROJECT_ID.iam.gserviceaccount.com" \
    --role="roles/trafficdirector.client"

gcloud projects add-iam-policy-binding PROJECT_ID \
    --member="serviceAccount:RUN_CLIENT_SA@PROJECT_ID.iam.gserviceaccount.com" \
    --role="roles/cloudtrace.agent"

Replace the following:

  • PROJECT_ID: your Google Cloud project ID.
  • RUN_CLIENT_SA: the name of the service account attached to your Cloud Run service.

If the service identity lacks these roles, the Cloud Run resource still deploys, but features that use ambient networking don't work.

For a list of IAM roles and permissions that are associated with Cloud Run, see Cloud Run IAM roles and Cloud Run IAM permissions. Configure ambient networking

Configure ambient networking by using gcloud or a YAML file.

gcloud

  • To enable ambient networking on a new service, pass the --ambient-networking flag and, optionally, the --ambient-scope flag:

    gcloud beta run deploy SERVICE \
  --image=IMAGE_URL \
  --ambient-networking \
  --ambient-scope=SCOPE \
  --region=REGION

  • To enable ambient networking on an existing service, pass the same flags to the gcloud beta run services update command, which deploys a new revision with ambient networking enabled:

    gcloud beta run services update SERVICE \
  --ambient-networking \
  --ambient-scope=SCOPE \
  --region=REGION

  • To disable ambient networking, pass the --no-ambient-networking flag:

    gcloud beta run services update SERVICE \
  --no-ambient-networking \
  --region=REGION

Replace the following:

  • SERVICE: the name of your Cloud Run service.
  • IMAGE_URL: a reference to the container image, for example, us-docker.pkg.dev/cloudrun/container/hello:latest. If you use Artifact Registry, the repository REPO_NAME must already be created. The URL follows the format of LOCATION-docker.pkg.dev/PROJECT_ID/REPO_NAME/PATH:TAG .
  • SCOPE: the ambient networking scope, either global or regional.
  • REGION: the region for your service.

YAML

  1. If you are creating a new service, skip this step. If you are updating an existing service, download its YAML configuration:

    gcloud run services describe SERVICE --format export > service.yaml

  2. Add the run.googleapis.com/ambient-networking annotation and, optionally, the run.googleapis.com/ambient-scope annotation:

    spec:
 template:
   metadata:
     annotations:
       run.googleapis.com/ambient-networking: 'true'
       run.googleapis.com/ambient-scope: SCOPE

    Replace SCOPE with the ambient networking scope, either global or regional. To disable ambient networking, set run.googleapis.com/ambient-networking to 'false' and remove the run.googleapis.com/ambient-scope annotation.

  3. Create or update the service using the following command:

    gcloud run services replace service.yaml

    The gcloud run services replace command defaults to using service.yaml file if present.

View ambient networking settings

To view the current ambient networking settings for your Cloud Run service:

Console

  1. In the Google Cloud console, go to the Cloud Run Services page:

    Go to Cloud Run

  2. Click the service to open the Service details page.

  3. Click the Networking tab.

  4. In the Ambient networking card, view the Scope setting.

gcloud

  1. Use the following command:

    gcloud beta run services describe SERVICE \
   --region=REGION

  2. Locate the run.googleapis.com/ambient-networking and run.googleapis.com/ambient-scope annotations in the returned configuration.
